## 目的

Yambda の 50M・500M・5B それぞれから、本研究のラベル付きペア表（T1/T2/O2 の起点、B/C の再聴秒数、活動日数）を作って公開する。
Phase 1 では、(1) 研究室サーバーで 50M の既存結果を完全に再現できること、(2) 500M を分割なしで作ったときのピークメモリ・時間・ディスク使用量、(3) 50M が 500M の部分集合として一致するか、を確かめる。5B をいくつに分割すれば安全かは、この実測から決める。

## 実行環境

- 研究室の共有 Linux サーバー（Ubuntu 22.04、40 コア、RAM 125 GiB、GPU は使わない）。他の利用者がいる。
- 作業ディレクトリ：`/data3/taiyo/`。リポジトリは `/data3/taiyo/organic-relisten-bench`（ブランチ `dataset-release`）。
- データの置き場所：`/data3/taiyo/relisten-data/<scale>/`（`raw/`、`processed/`、`results/`、`tmp/`）。リポジトリの `data/` と `results/` は使わない。
- Python はシステムの 3.10 ではなく、uv で入れた 3.13 の `.venv` を使う。sudo は使わない。

## 正とする定義（変えない）

- `src/relisten/config.py` の `LOWER_BOUND_DAYS=1`、`HORIZON_DAYS=90`、`SPLITS`、`SECONDS_PER_DAY=86400`、`SENSITIVITY_LOWER_DAYS`。
- `labels.py` の `build_pairs`・`activity_counts`・`label_expr`・`with_labels` の SQL と式（起点の選び方、同一 5 秒ビンで経路が混ざる初接触の除外、窓 `[L*86400, H*86400]`、活動日数の数え方）。
- timestamp は秒（5 秒刻み）。`day = timestamp // 86400`。5 倍しない。

## 入力

- Hugging Face `yandex/yambda`、**リビジョン `dd6f3a19eef5866e346c3270e098baa641a44948` に固定**（既存の 50M 結果と同じ）。`ensure_raw` は現在、最新のリビジョンを取得するので、固定できるようにする。
- 50M：`flat/50m/listens.parquet`、`flat/50m/likes.parquet`（約 0.38 GB）
- 500M：`flat/500m/listens.parquet`、`flat/500m/likes.parquet`（約 3.8 GB）
- サイズと sha256 はリビジョン固定の API（`/api/datasets/yandex/yambda/revision/<rev>?blobs=true`）で取り、manifest に記録して照合する。
- 再現の基準：リポジトリにコミット済みの `results/dataset_summary.csv`、`results/split_summary.csv`、`results/label_sensitivity.csv`、`results/anchor_counts.csv`。

## 作るもの

1. **規模の切り替え**：環境変数（例：`RELISTEN_SCALE`=50m|500m|5b、`RELISTEN_DATA_ROOT`、`RELISTEN_RESULTS`、`RELISTEN_DUCKDB_MEMORY`、`RELISTEN_DUCKDB_THREADS`）で、取得するファイル・データの置き場所・集計表の出力先・DuckDB の上限を切り替える。**環境変数がなければ、今とまったく同じ動作**（50M、`data/`、`results/`、5GB・4 スレッド）にする。名前と実装は Codex が決めてよい。
2. **一括実行スクリプト** `scripts/build_release.py --scale <s>`：取得 → 照合 → `user_days` → `build_pairs` → `prepare_labels` を順に行う。表現学習用の抽出（`representation_train.parquet`）と埋め込みの処理は、このタスクでは行わない。各段階の開始・終了時刻をログに残す。
3. **計測の記録** `release/<scale>/run_metrics.json`（リポジトリ内、小さいファイル）：段階ごとの実時間、`/usr/bin/time -v` の最大 RSS、DuckDB の一時ファイルの最大量、データディレクトリの最大使用量、DuckDB のメモリ上限・スレッド数、開始時の `free -g` の available。
4. **一致の確認表** `release/consistency_500m_vs_50m.json`：
   - 50M の uid のうち 500M にある割合
   - 50M の uid に絞った 500M の生ログが、50M の生ログと行単位で一致するか（行数と、並べ替えた全列のハッシュ）
   - 50M の uid に絞った 500M の `pairs.parquet` が、50M の `pairs.parquet` と一致するか（列ごと）。両規模の `max_timestamp` も記録する。違う場合、`complete_followup_*` の違いはそれで説明できるかを書く。
5. 500M の集計表（`dataset_summary.csv`、`split_summary.csv`、`label_sensitivity.csv`、`anchor_counts.csv`）を `release/500m/` に置く。

## 手順

1. 環境：uv で Python 3.13 の `.venv` を作り、`uv pip install -e .` で基本の依存だけを入れる（`official` の追加依存は不要）。`requirements.lock` は macOS で作ったものなので、Linux で入らない場合は基本の依存だけを入れ、入れた版を `release/environment.txt` に `uv pip freeze` で残す。`pytest -q` が通ることを確かめる（35 件）。
2. 開始前に `free -g` と `df -h /data3` を記録する。available が 60 GiB 未満、または /data3 の空きが 120 GiB 未満なら始めずに止まる。
3. **50M の再現**：既定の定義のまま、`RELISTEN_SCALE=50m` でサーバー上のデータディレクトリに作る。コミット済みの 4 つの集計表と完全に一致することを確かめる（CSV の差分がゼロ）。
4. **500M**：分割せずに作る。DuckDB は `memory_limit=48GB`、`threads=16` から始める（他の利用者のために上限を設ける）。`/usr/bin/time -v` で全体を包んで計測する。
5. 一致の確認（作るもの 4）。
6. 5B の見積もり：500M の実測（最大 RSS、一時ファイル、出力サイズ）をユーザー数に比例させて 5B を見積もり、**1 回分のピーク RSS が 40 GiB 以下**になる uid の分割数を提案する。見積もりの前提を書く。5B は取得しない。

## 変えてはいけないもの

- 上の「正とする定義」。
- リポジトリにコミット済みの `results/` 以下のすべてのファイル（作業の前後で sha256 を照合し、報告に書く）。
- `main` ブランチ。push するのは `dataset-release` だけ。
- `/data3/taiyo/` の外のファイル。他の利用者のプロセス。

## Codex が自分で決めてよいこと（DECISIONS.md に記録する）

- 環境変数の名前、スクリプトの構成、ログの形式。
- DuckDB の上限の調整（ピーク RSS が予算内に収まる範囲で）。
- `requirements.lock` が Linux で使えないときの依存の入れ方。

## 完了条件

- テスト：既存の 35 件が通る。規模の切り替えについて、「環境変数なしなら既定の 50M のパスと設定になる」ことを確かめるテストを 1 件足す。
- 検算：50M の 4 つの集計表がコミット済みのものと完全に一致する。
- 出力：`release/500m/` の集計表と `run_metrics.json`、`release/consistency_500m_vs_50m.json`、5B の分割数の提案。
- コミット済みの `results/` の sha256 が前後で一致する。

## 止まって聞く条件

- 50M の集計表が 1 行でも一致しない（原因を特定せずに 500M に進まない）。
- 定義（config.py の値、labels.py の SQL や式）を変えないと進めない。
- ピーク RSS が 90 GiB を超えそう、または available が 30 GiB を切った（他の利用者への影響を避けて、すぐ止める）。
- /data3 の空きが 100 GiB を切った。
- 50M の uid に絞った 500M の生ログが 50M と一致しない（入れ子だという前提が崩れる。記録して止まる）。
- 予算の 2 倍（実時間 12 時間）を超える。
- 取得に認証や有料サービスが必要になる。
